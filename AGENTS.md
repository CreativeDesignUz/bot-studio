# Bot Studio — правила для AI-разработки

Эти правила обязательны для Codex, ChatGPT, GitHub Copilot и других AI-агентов, работающих с репозиторием.

## Перед началом работы

1. Прочитать этот файл, `docs/ARCHITECTURE.md` и связанные с задачей документы.
2. Проверить текущую ветку, `git status`, remote и актуальность `origin/main`.
3. Не перезаписывать незнакомые изменения. Не использовать `git push --force` и `git reset --hard`.
4. Работать в отдельной ветке и Pull Request. Не выполнять merge в `main` самостоятельно.

## Источники истины

- Приложение: Next.js 16, React 19, TypeScript, Vinext и Cloudflare Workers.
- Runtime-конфигурация создаётся командой `npm run build` в `dist/server/wrangler.json`.
- Cloudflare — единственная поддерживаемая серверная платформа. Не менять архитектуру ради Vercel-проверки.
- Основное хранилище и Auth — Supabase. D1/R2 из `.openai/hosting.json` относятся к локальному шаблону и не должны попадать в Cloudflare build.
- Staging: Worker `bot-studio-staging`, Supabase ref `eslbcwopolrxoptcxqhp`.
- Production: Worker `bot-studio`, Supabase ref `xpylzfdwudtaceysfcwd`.
- Production запрещено изменять или публиковать без отдельного явного разрешения пользователя.

## Архитектурные ограничения

- Не создавать параллельные реализации уже существующих API, экранов и бизнес-логики.
- Интерфейс продавца (`/workspace`) и покупательский Mini App (`/miniapp`) должны оставаться разделёнными.
- Каждый seller API обязан проверять авторизацию и принадлежность бота владельцу.
- Telegram `initData` проверяется только на сервере с токеном конкретного подключённого бота.
- Токены Telegram, Supabase service key, OAuth secrets и cookies запрещено выводить в клиент, URL, логи, тестовые снимки или Git.
- Обновления JSON-настроек должны объединять существующие поля, а не перезаписывать объект целиком.
- Webhook, checkout, onboarding и публикация должны быть идемпотентными.
- Наличие экрана или кнопки не считается работающей функцией: проверять API, сохранение и чтение после refresh.
- Не заменять рабочий сценарий mock-данными. Demo-данные допустимы только в явно изолированном preview.
- Для критических переходов между страницами использовать обычный HTTPS-переход (`<a href>`), пока Vinext RSC-навигация не будет обновлена и отдельно проверена.

## Supabase и миграции

- Не удалять данные, таблицы и миграции.
- Новую миграцию сначала проверить статически и на чистой тестовой схеме.
- Применять миграции только к Staging после явного разрешения. Production-базу не трогать.
- RLS и server-side owner checks должны защищать данные разных предпринимателей независимо друг от друга.
- Не коммитить `.env*`, `supabase/.temp/`, `.wrangler/`, секреты и локальные ключи.

## Cloudflare

- Перед staging deploy выполнить `npm run check`.
- Проверить `npm run verify:cloudflare`; D1/R2 bindings в итоговой сборке запрещены.
- Staging публикуется только как `bot-studio-staging` и только с `--strict --keep-vars`.
- Не запускать `wrangler deploy` без явного `--name bot-studio-staging`.
- Не менять remote secrets из кода или CI. Секреты хранятся в Cloudflare/GitHub environments.
- Не заявлять об успешном deploy без проверки постоянного HTTPS URL и smoke-тестов.

## Обязательные проверки

После изменений всегда выполнить:

1. `npm run typecheck`
2. `npm run lint`
3. `npm test`
4. `npm run build`
5. `npm run verify:cloudflare`
6. Ручную проверку затронутого пользовательского сценария на desktop и mobile, если менялся UI.

Сообщить о предупреждениях, непроверенных сценариях и известных рисках. Не называть задачу завершённой, если обязательный критерий не проверен.

## Git и GitHub

- Использовать Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`.
- После успешных проверок разрешён commit и push только в согласованную рабочую ветку.
- Не отправлять изменения напрямую в `main`, не выполнять merge и production deployment.
- Pull Request должен содержать: причину, изменения, тесты, ручную проверку, риски и миграции.
- Не обходить обязательные GitHub checks и не ослаблять правила репозитория ради зелёного статуса.
