# Bot Studio — обязательные инженерные и QA-правила

## Правило каждого изменения
1. Работать через отдельную ветку и Pull Request; никаких прямых изменений production ради проверки.
2. До изменения указать затрагиваемый сценарий, угрозы, критерии приемки и способ отката.
3. Для любого исправленного дефекта добавлять регрессионный тест, который падает до исправления.
4. После каждой отправки коммита запускать CI: TypeScript, ESLint, unit/security tests, dependency audit, build.
5. При любом failed/cancelled/unknown check PR не сливать. Не скрывать ошибки и не снижать строгость проверок, чтобы добиться зелёного статуса.
6. Для изменений backend/database обязательно проверять owner/bot isolation, неверные входные данные и повтор запросов.
7. Для изменений UI покрывать Default, Hover, Focus, Active, Disabled, Loading, Empty, Error, Success (где применимо), клавиатуру, мобильный viewport и accessibility.
8. Никаких реальных токенов, персональных данных и платёжных реквизитов в логах, фикстурах, скриншотах и PR.
9. Перед выпуском в staging применить миграции, проверить чистую миграцию и повторное выполнение, а затем провести интеграционный E2E в безопасной тестовой среде.
10. В production выпускать только после положительного QA-отчёта и возможности отката. Любой P0/P1 запрещает релиз.

## Матрица приоритетов
- P0: подмена владельца, утечка токенов, обход Telegram auth, необоснованное списание денег, межтенантный доступ. Немедленно блокировать.
- P1: заказ не создаётся, создаётся дважды, неверная сумма, теряются order_items, доступ к чужому заказу, неверный статус оплаты. Блокировать.
- P2: сбои интерфейса, доступности, медленная загрузка, ошибки отдельных некритичных операций. Требовать исправления или оформленного исключения.
- P3: косметика и малозаметные несоответствия. Вести в backlog.

## QA-сценарий заказа — каждый backend PR
1. Корректный Telegram initData от правильного project bot: авторизация проходит.
2. Неверный бот, поврежденный HMAC, отсутствующая подпись, повторённые поля, устаревшая и будущая сессия: отклонять.
3. Покупатель не получает доступ к seller /workspace и API управления бизнесом.
4. Покупатель отправляет список id/quantity; итоговые цены получает только сервер из каталога соответствующего bot_id.
5. Товар другого бота, неактивный, несуществующий, неправильная валюта, количество 0/100, дубликат ID и пустая корзина: отклонять.
6. Повторение запроса с тем же idempotency key возвращает тот же order id без дубликата строк.
7. Два одновременных одинаковых запроса не создают два заказа.
8. Искусственная ошибка вставки order_items откатывает целиком создание orders.
9. Проверка сумм, истории, статусов оплаты и доставки на уровне Supabase и seller dashboard.
10. Telegram token/manager недоступен, Supabase недоступен, тайм-аут: безопасный отказ без потери согласованности.
11. Ограничение частоты запросов и размера тела, проверка headers/CORS/CSRF для seller API, отдельная оценка cookies.
12. Live staging: bot /start → buyer Mini App → каталог → корзина → checkout → orders → seller dashboard.

## Текущие блокирующие ограничения
- Unit/security tests запускаются в GitHub Actions автоматически; это ещё НЕ browser E2E или QA-агент с доступом к Telegram.
- Buyer storefront и cart отсутствуют в проверенном репозитории; сценарий 12 не может считаться пройденным.
- SQL миграция ещё не применена в staging.
- PR не мержить и не деплоить до реального end-to-end и ручной проверки интеграции.
- Все skipped тесты являются QA-debt. Запрещено интерпретировать их как прохождение сценария.
